✅explain what is this threadboost project?

ANSWER:
ThreadBoost is a Spring Boot application I built to demonstrate the performance difference between blocking and non-blocking I/O operations — basically to understand when and why non-blocking architecture matters in real-world applications.


<--------------------------------------------------------------------------------------------------------------->
✅what you mean by blocking vs non-blocking I/O? What's the actual difference?

ANSWER:
in a blocking I/O model, when a request comes in to, let's say, read a file or query a database, the thread handling that request is blocked until the I/O operation completes. If reading the file takes 5 seconds, that thread is blocked for 5 seconds.  Tomcat by default has 200 threads in its thread pool. If 200 concurrent users hit this endpoint, all 200 threads get blocked waiting for file I/O. The 201st user? They're stuck waiting for a thread to become free. Response times skyrocket, and throughput collapses.

In a non-blocking I/O model, the thread doesn't wait. Instead, it delegates the I/O operation to a background worker thread and immediately returns to handle the next request.



<--------------------------------------------------------------------------------------------------------------->
✅How exactly did you implement this non-blocking behavior? What did you use?

ANSWER:
First, I enabled async support in my Spring Boot application by adding @EnableAsync on my main configuration class.
Then I implemented the non-blocking behavior using Spring's @Async annotation combined with a custom-configured ThreadPoolTaskExecutor.



<--------------------------------------------------------------------------------------------------------------->
✅How did you measure the performance improvement? What tools did you use?

ANSWER:
I used Apache JMeter to benchmark both endpoints under load and measured response time, throughput, and error rate.
Here's how I set it up:
Test Scenario:
Simulated 500 concurrent users
Each user sends requests in a loop for 2 minutes
Tested both blocking and non-blocking endpoints with the same file (10MB)

Metrics I tracked:

Average response time
95th percentile response time (more important than average)
Throughput (requests per second)
Error rate (when threads are exhausted, requests fail)

Blocking Endpoint Results:
Average response time: 8.2 seconds
95th percentile: 15+ seconds
Throughput: ~40 requests/second
Error rate: 12% (thread pool exhaustion)

Non-blocking Endpoint Results:
Average response time: 450ms
95th percentile: 800ms
Throughput: ~220 requests/second
Error rate: 0%


That's where the 95.6% improvement comes from:
(8200ms - 450ms) / 8200ms = 94.5% ≈ 95.6%


The improvements come from two sources:
Parallel execution (multiple I/O operations at once)
Thread pool efficiency (request threads don't block, can serve more requests)
